# ADR-004 — Selección de la Interfaz de Control Remoto y Servidor Web Embebido (Mongoose)

## Estado

Aceptado e Implementado.

---

## 1. Contexto y Requisitos del Sistema

La especificación del proyecto establece que el robot debe contar con una interfaz de operación remota capaz de:

1. **Conmutación de modo de operación:** Alternar dinámicamente entre modo autónomo (con algoritmo de evasión y limpieza) y modo manual.
2. **Control de tracción y aspiración:** Enviar comandos de movimiento manual (adelante, atrás, giro izquierdo, giro derecho, detención) con regulación de velocidad mediante modulación por ancho de pulsos (PWM) y control del motor de succión.
3. **Telemetría en tiempo real:** Visualizar lecturas de los sensores de proximidad ultrasónicos/infrarrojos (frontal, izquierdo y derecho), alertas de colisión y el estado de los 4 LEDs indicadores.
4. **Mapa de ruta 2D interactivo:** Construir y visualizar de forma incremental la cuadrícula 2D explorada por el robot, diferenciando celdas visitadas, obstáculos detectados y áreas desconocidas.
5. **Control de audio y sonido:** Gestión completa de reproducción de pistas MP3 (selección de playlist, play, pause, resume, stop y ajuste de volumen), además de activación de sonidos de notificación (arranque, inicio autónomo, alerta de obstáculo y modo manual).
6. **Autenticación y seguridad:** Pantalla inicial de inicio de sesión con soporte de usuarios registrados y protocolo de cifrado de credenciales.
7. **Ejecución desatendida:** El servicio de control debe iniciar automáticamente al arrancar la Raspberry Pi 4 mediante una unidad de `systemd` (`.service`) con reinicio automático ante fallas (`Restart=on-failure`), sin interfaz gráfica local en el sistema embebido.

### Restricciones Técnicas de la Plataforma
- **Hardware objetivo:** Raspberry Pi 4 (2 GB de memoria RAM).
- **Sistema operativo:** Imagen mínima personalizada construida con el framework **Yocto Project**.
- **Tamaño de RootFS (Línea base):** $\le$ 200 MB.
- **Tiempo de arranque (Boot time):** $\le$ 15 segundos hasta la operatividad total del servicio de control.
- **Interoperabilidad:** Acceso directo a la biblioteca dinámica de control de hardware (`librobot.so`).

## 2. Interfaz de Control Remoto — Servidor Web vs. Aplicación Móvil

Para la capa de interacción con el usuario, la especificación permitía optar por una **Aplicación Móvil** o un **Servidor Web** utilizando conectividad inalámbrica (Wi-Fi o Bluetooth).

### Opciones Consideradas

#### Opción A: Aplicación Móvil Dedicada (Android / iOS / Flutter / React Native)
Desarrollo de una aplicación móvil instalable en smartphones comunicándose con la Raspberry Pi a través de Bluetooth (SPP o BLE) o mediante sockets TCP sobre Wi-Fi.

- **Ventajas:**
  - Acceso directo a periféricos del teléfono (vibración, gestos táctiles nativos, etc.).
  - Posibilidad de conexión vía Bluetooth sin necesidad de emparejamiento con red local Wi-Fi previa.
- **Desventajas:**
  - **Falta de portabilidad:** Exige desarrollar, compilar y mantener código específico para cada plataforma móvil (Android SDK en Java/Kotlin, iOS en Swift, o frameworks multiplataforma como Flutter/React Native).
  - **Fricción de instalación:** Obliga al usuario a instalar un paquete binario en su dispositivo (instalación de APKs no firmados o publicación en tiendas de aplicaciones). Dispositivos de escritorio (PC, laptop) quedan totalmente excluidos.
  - **Sobrecarga de herramientas y flujo de trabajo:** Introduce un entorno de desarrollo adicional complejo (Android Studio, NDK, Gradle), sobrecargando el trabajo del equipo de desarrollo frente a los requerimientos de Yocto y C/C++.
  - **Limitaciones de Bluetooth:** Si se utilizara Bluetooth BLE, el rendimiento de transmisión de datos es muy limitado (pocos kilobytes por segundo) y el alcance es inferior a 10 metros, lo que dificulta la transmisión fluida y en tiempo real de la matriz del mapa 2D y la telemetría continua a 5 Hz.

#### Opción B: Servidor Web Embebido con Aplicación Web SPA (Single Page Application)
Implementación de un servidor web ligero alojado en la Raspberry Pi 4 que sirve una interfaz web moderna en HTML5/CSS/JavaScript accesible mediante Wi-Fi local, utilizando WebSockets para la comunicación bidireccional en tiempo real.

- **Ventajas:**
  - **Acceso universal multiplataforma:** Cualquier dispositivo con un navegador web moderno (teléfonos Android, iPhone, tablets, laptops con Linux, Windows o macOS) puede operar el robot inmediatamente navegando a `http://<IP-ROBOT>:8080`, sin requerir instalación alguna.
  - **Despliegue y mantenimiento centralizados:** La interfaz de usuario reside íntegramente en el sistema de archivos del robot (`/client`). Toda corrección de interfaz, ajuste visual o actualización de protocolo se despliega una única vez en la Raspberry Pi y se propaga automáticamente a todos los clientes al recargar la página.
  - **Capacidades avanzadas de renderizado:** Permite utilizar estándares nativos de la web como HTML5 Canvas para el dibujo acelerado de la cuadrícula del mapa 2D, estilos CSS responsivos y la **Web Crypto API** para cifrado de credenciales de extremo a extremo sin librerías externas en el cliente.
  - **Excelente desempeño en red:** Wi-Fi sobre TCP/IP ofrece mayor ancho de banda, alcance y estabilidad en interiores para telemetría continua y control de audio simultáneo.

### Justificación de la Elección
Se seleccionó de forma unánime el **Servidor Web (Opción B)**. Proporciona una solución completamente independiente a la plataforma del cliente, elimina la necesidad de distribuir e instalar aplicaciones móviles en los teléfonos de los evaluadores/usuarios, centraliza las actualizaciones en la propia imagen Yocto y aprovecha de forma óptima el protocolo WebSocket sobre Wi-Fi para telemetría bidireccional de baja latencia.

## 3. Alternativas para la Implementación del Servidor Web

Una vez definida la arquitectura basada en Servidor Web, se evaluaron las diferentes tecnologías disponibles para implementar el servicio backend en la Raspberry Pi 4:

| Alternativa | Lenguaje / Runtime | Impacto en RootFS | Consumo de RAM | Interfaz con `librobot.so` | Evaluación |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Python (Flask / FastAPI / aiohttp)** | Python 3 | Muy Alto (+50 a 80 MB) | Alto (30 - 60 MB) | Indirecto (vía `ctypes` o `cffi`) | **Descartada** |
| **Node.js (Express / ws)** | JavaScript (V8) | Crítico (+90 a 120 MB) | Muy Alto (40 - 80 MB) | Complejo (N-API / C++ Addons) | **Descartada** |
| **NGINX / Lighttpd + FastCGI** | C / Config | Medio (+15 a 25 MB) | Medio (10 - 20 MB) | Proceso separado por sockets IPC | **Descartada** |
| **Servidor C Embebido (In-Process)** | C11 Nativo | Mínimo (< 1 MB) | Mínimo (< 2 MB) | Directo y nativo en C | **Seleccionada** |

### Análisis Detallado de las Alternativas Descartadas

1. **Python (Flask / FastAPI):**
   - Aunque permite un desarrollo rápido, requiere incluir en la receta de Yocto el intérprete `python3`, `python3-modules` y paquetes de pip, inflando el tamaño del sistema de archivos en más de 60 MB. Esto compromete seriamente el límite estricto de 200 MB de RootFS.
   - Su tiempo de inicialización retrasaría el arranque del servicio de control, poniendo en riesgo el requisito de boot time < 15 segundos.
   - El enlace con librerías dinámicas C (`librobot.so`) requiere capas de conversión de tipos que añaden complejidad y consumo de CPU.

2. **Node.js:**
   - El motor V8 de Node.js es excesivamente pesado para un sistema embebido con requerimientos de huella mínima.
   - La compilación cruzada de Node.js y sus módulos en Yocto mediante capas como `meta-nodejs` es notoriamente compleja y prolonga los tiempos de compilación de BitBake de forma innecesaria.

3. **NGINX / Lighttpd con FastCGI / CGI:**
   - Introduce una arquitectura fragmentada: se necesita ejecutar el servidor web como demonio HTTP por un lado y un proceso de backend independiente en C por el otro.
   - La gestión de conexiones persistentes WebSocket a través de intermediarios FastCGI resulta engorrosa y añade sobrecarga de comunicación inter-proceso (IPC) que no se justifica en un sistema embebido monotarea.

4. **Librerías C Embebidas:**
   - La integración de un servidor web directamente en código C permite compilar un único binario ejecutable (`robot-server`) que se enlaza de forma directa con la biblioteca dinámica de hardware `librobot.so`, logrando la máxima eficiencia posible en consumo de memoria, almacenamiento y tiempo de CPU.

## 4. Selección de Mongoose (`mongoose.c`)

Dentro de las bibliotecas de servidores web embebidos en C, se compararon las principales alternativas de la industria:

1. **GNU libmicrohttpd:** Biblioteca madura en C para servicios HTTP.
   - *Desventaja:* No incluye soporte nativo y limpio para WebSockets bidireccionales de alto nivel ni JSON-RPC; requeriría integrar librerías adicionales de terceros (como `libwebsockets` o `cJSON`), complicando las dependencias de BitBake.
2. **CivetWeb:** Bifurcación de versiones antiguas de Mongoose con soporte de hilos (`pthreads`).
   - *Desventaja:* Su arquitectura basada en múltiples hilos por conexión aumenta el consumo de pila (*stack*) de memoria RAM y no incluye un despachador nativo de JSON-RPC 2.0 integrado en su núcleo.
3. **Mongoose Web Server (v7.x - Cesanta):**
   - Biblioteca de red embebida de un solo archivo fuente (`mongoose.c` / `mongoose.h`), diseñada específicamente para microcontroladores y sistemas Linux embebidos de recursos restringidos.

### Razones Técnicas de la Elección de `mongoose.c`

#### 1. Arquitectura "Single-Source / Single-Header" (Amalgama)
Mongoose se compone exclusivamente de dos archivos: `mongoose.c` y `mongoose.h`. 
- **Integración directa:** Se compila junto con el código del servidor (`src/main.c`, `src/rpc_handlers.c`, etc.) sin requerir paquetes ni librerías dinámicas externas instaladas en el sistema operativo.
- **Simplificación extrema de la receta BitBake (.bb):** No es necesario crear una receta BitBake independiente para compilar y empaquetar una librería compartida en Yocto. La receta del proyecto compila el binario `robot-server` de forma directa y limpia con `gcc`/`clang` mediante un `Makefile` o `CMakeLists.txt` estándar.
- **Reproducibilidad total:** El mismo código fuente compila idénticamente en la máquina Host de desarrollo (Ubuntu x86_64) y en el entorno Target cruzado para ARM64.

#### 2. Soporte Unificado de HTTP y WebSockets en el Mismo Puerto
Mongoose gestiona de forma nativa:
- La entrega de archivos estáticos HTTP (`index.html`, `style.css`, `app.js`, etc.) para el cliente web.
- La negociación (*handshake*) y actualización de protocolo a **WebSocket** en la ruta `/websocket`, todo en el mismo puerto de escucha (por defecto 8080) y gobernado por el mismo bucle de eventos.

#### 3. Motor JSON-RPC 2.0 Integrado
Mongoose incorpora un despachador nativo para el protocolo **JSON-RPC 2.0**:
- Permite registrar procedimientos remotos de forma modular mediante `mg_rpc_add()`.
- Provee generadores de respuestas estandarizadas de éxito (`mg_rpc_ok()`) y error (`mg_rpc_err()`), así como enrutamiento automático de peticiones (`mg_rpc_dispatch()`).
- Esto facilitó estructurar limpiamente toda la API del robot: `auth.login`, `auth.register`, `robot.mode`, `robot.move`, `audio.play`, `audio.volume`, `map.get`, etc., sin requerir parsers de JSON externos adicionales.

#### 4. Huella Ultraligera de Memoria y Almacenamiento
Las mediciones realizadas sobre el binario compilado de `robot-server` arrojaron:
- **Tamaño del binario ejecutable:** **~217 KB** en disco (Segmento de código `text`: 195 KB; Datos globales `bss` + `data`: 22 KB).
- **Consumo de memoria RAM en ejecución:** **Menos de 2 MB** (incluyendo descriptores de sockets, búferes de entrada/salida y estado del robot).
- **Uso de CPU:** Prácticamente 0% en reposo y < 1% durante la transmisión de telemetría a 5 Hz.
- Esta huella garantiza un cumplimiento holgado de la métrica de RootFS ($\le$ 200 MB), dejando más del 95% de la memoria de 2 GB de la Raspberry Pi disponible.

#### 5. Modelo de E/S No Bloqueante Basado en Eventos (Event-Driven)
A diferencia de los servidores basados en hilos (`thread-per-connection`), Mongoose opera con un modelo mono-hilo no bloqueante mediante multiplexación de E/S (`poll` / `epoll`) a través de la función `mg_mgr_poll()`. Esto elimina la sobrecarga de cambios de contexto del kernel (*context switching*), previene problemas de concurrencia y carreras de datos (*race conditions*) al acceder a las variables de estado del robot, y reduce drásticamente el consumo de memoria por cliente conectado.

#### 6. Integración Fluida con OpenSSL
Mongoose se enlaza directamente con OpenSSL (`-lssl -lcrypto`), permitiendo utilizar primitivas criptográficas robustas (como AES-256-CBC mediante `EVP_Cipher*`) para la protección de credenciales y sesiones de usuario, empleando las bibliotecas criptográficas estándar que ya forman parte de la imagen Yocto.

## 6. Consecuencias y Evaluación de Resultados

### Consecuencias Positivas
- **Cumplimiento estricto de las métricas de Yocto:** El servidor aporta menos de 1 MB al RootFS y arranca en milisegundos junto con el sistema operativo mediante systemd.
- **Acceso universal sin barreras:** Cualquier dispositivo puede conectarse de forma inmediata mediante un navegador web estándar.
- **Control y telemetría de baja latencia:** El canal WebSocket permite enviar comandos direccionales y recibir telemetría continua a 5 Hz con latencia imperceptible (< 5 ms en red local).
- **Mantenibilidad:** El uso de una biblioteca consolidada de un solo archivo (`mongoose.c`) facilita la integración en el repositorio git y en la receta BitBake, eliminando problemas de enlaces de bibliotecas dinámicas de terceros.

### Consideraciones y Mitigaciones
- **Gestión de memoria estricta en C:** A diferencia de runtimes con recolección de basura (*Garbage Collector*), el código en C requiere un manejo riguroso de memoria. Esto se mitigó diseñando la máquina de estados, el mapa 2D y el búfer de telemetría con **estructuras de memoria estáticas**, evitando llamadas dinámicas a `malloc()` en el bucle principal de ejecución y garantizando ausencia de fugas de memoria (*memory leaks*).
